# 05. アプリ開発演習 — BLE センサモニタを作る

01〜04 で学んだ UI・イベント・インテント・BLE を組み合わせ、1 本のアプリを要件定義から完成まで作ります。演習では「動いた」で終わらせず、設計を書き、テストし、振り返るところまでを一連の流れとして体験します。

## 1. 開発の流れ

```text
要件定義 → 画面設計 → クラス設計 → 実装（小さく作って動かす）→ テスト → 振り返り
   ↑                                                              │
   └──────────────────── 改善点を次の繰り返しへ ──────────────────┘
```

一度に全部作らず、**動く最小のもの** を作ってから機能を足していきます。

## 2. 題材: BLE センサモニタ

### 2.1 要件

| No. | 要件 | 優先度 |
| --- | --- | --- |
| R1 | 周辺の対象機器をスキャンして一覧表示する | 必須 |
| R2 | 一覧から機器を選んで接続する | 必須 |
| R3 | 温度を通知（Notify）で受け取り、リアルタイムに表示する | 必須 |
| R4 | ボタンで機器の LED を点灯・消灯する | 必須 |
| R5 | 切断されたら画面に表示し、再接続ボタンを出す | 必須 |
| R6 | 温度がしきい値を超えたら警告表示する | 任意 |
| R7 | 測定値を他のアプリに共有する | 任意 |

**非機能要件**（性能・使いやすさなど）も決めます。

- 権限がない・Bluetooth がオフのときは、理由と対処を画面に表示する（黙って何もしない状態にしない）。
- スキャンは 10 秒で自動停止する。
- 画面を回転しても接続が切れない。

### 2.2 画面設計

```text
┌───────────────────┐        ┌───────────────────┐
│ 機器を探す         │        │ Sensor-01   接続中 │
├───────────────────┤  タップ  ├───────────────────┤
│ [スキャン開始]     │ ───────→ │                   │
│                   │ Intent  │     23.45 ℃       │
│ Sensor-01  -48dBm │ (アドレス) │                   │
│ Sensor-02  -71dBm │        │ LED  [ ON | OFF ]  │
│                   │        │                   │
│                   │        │ [共有]  [切断]     │
└───────────────────┘        └───────────────────┘
   ScanActivity                  DeviceActivity
```

画面ごとに「表示する情報」「操作」「遷移先」を表にしておくと、実装の抜けが減ります。

### 2.3 クラス設計

```text
ScanActivity ── RecyclerView で一覧表示 ── タップ → DeviceActivity（Intent でアドレスを渡す）
DeviceActivity ── 表示と操作 ──→ DeviceViewModel（状態を保持。回転しても残る）
                                     │
                                     ▼
                               BleDeviceClient（接続・GATT 操作・キュー管理）
                                     │
                               TemperatureParser（バイト列 → ℃ の変換）
```

- **画面（Activity）に BLE の処理を直接書かない**。通信は `BleDeviceClient` に分け、画面は表示と操作だけを担当する（単一責任）。
- バイト列の変換は Android に依存しない `TemperatureParser` に分けると、**JUnit で単体テスト** できる（[Java ノートのテスト技法](../../../01_fundamentals/java（Java言語）/04_testing/README.md)）。

## 3. 実装のステップ

| ステップ | 内容 | 確認方法 |
| --- | --- | --- |
| 0 | nRF Connect で対象機器の UUID・データ形式を確認する | nRF Connect で読み書き・通知ができる |
| 1 | 2 画面と画面遷移を作る（BLE なし、ダミーデータ） | 一覧のタップで詳細画面にアドレスが渡る |
| 2 | 権限の要求と Bluetooth 有効化の依頼 | 拒否・許可の両方で正しく表示される |
| 3 | スキャンして一覧に表示 | 対象機器だけが重複なく表示され、10 秒で止まる |
| 4 | 接続・サービス探索・切断 | Logcat で状態変化を確認、切断時に表示が変わる |
| 5 | LED の書き込み | 機器の LED が点灯・消灯する |
| 6 | 温度の通知の受信と表示 | 機器を温めると表示が変わる |
| 7 | 任意機能（警告、共有） | 要件どおりに動く |

各ステップが終わるごとに動作確認し、Git にコミットします。問題が起きたら、直前のステップとの差分を見れば原因を絞り込めます。

## 4. テスト

### 4.1 単体テスト（JUnit）

```java
class TemperatureParserTest {
    @ParameterizedTest
    @CsvSource({
        "0x29, 0x09, 23.45",     // 0x0929 = 2345
        "0x00, 0x00, 0.00",
        "0xFF, 0xFF, -0.01",     // 負の値（符号付き）
    })
    void バイト列を摂氏に変換する(String low, String high, double expected) {
        byte[] value = {(byte) Integer.decode(low).intValue(), (byte) Integer.decode(high).intValue()};
        assertEquals(expected, TemperatureParser.parse(value), 0.001);
    }

    @Test
    void 長さが足りなければ例外() {
        assertThrows(IllegalArgumentException.class, () -> TemperatureParser.parse(new byte[] {0x01}));
    }
}
```

### 4.2 実機での確認（テスト項目表の例）

| No. | 観点 | 手順 | 期待結果 | 結果 |
| --- | --- | --- | --- | --- |
| T1 | 権限拒否 | 初回起動で権限を拒否する | 理由と設定画面への案内が表示される | |
| T2 | Bluetooth オフ | Bluetooth をオフにしてスキャン | 有効化の依頼が表示される | |
| T3 | スキャン | スキャン開始 | 対象機器が表示され、10 秒で止まる | |
| T4 | 接続 | 一覧の機器をタップ | 「接続中」と温度が表示される | |
| T5 | 書き込み | LED を ON → OFF | 機器の LED が追従する | |
| T6 | 切断 | 機器の電源を切る | 「切断されました」と再接続ボタンが出る | |
| T7 | 回転 | 接続中に画面を回転 | 接続が維持され、温度が表示され続ける | |
| T8 | 境界値 | しきい値ちょうど・前後の温度 | 仕様どおりに警告が出る・出ない | |

正常な流れだけでなく、**異常系**（権限拒否、電波が届かない、途中で切断）を必ず確認します。

## 5. デバッグの道具

| 道具 | 使い方 |
| --- | --- |
| Logcat | `Log.d(TAG, "onConnectionStateChange status=" + status)` のようにコールバックの値を出す |
| ブレークポイント | Android Studio のデバッガで止めて変数を確認する |
| `adb` | `adb devices`（接続端末の確認）、`adb logcat`、`adb install app.apk` |
| nRF Connect | アプリと機器のどちらに問題があるかを切り分ける |
| Bluetooth HCI スヌープログ | 開発者向けオプションで有効にすると、BLE の通信内容を記録できる |

実機でデバッグするには、端末の **開発者向けオプション** を有効にし（設定 → デバイス情報 → ビルド番号を 7 回タップ）、**USB デバッグ**（またはワイヤレスデバッグ）をオンにします。

## 6. 仕上げ

- **アイコン・アプリ名**: `res/mipmap/` と `strings.xml` の `app_name`。
- **リリースビルド**: Android Studio の Build → Generate Signed Bundle / APK で署名付きの APK / AAB を作る。署名の鍵（キーストア）は紛失すると更新版を出せないため安全に保管し、Git には入れない。
- **README**: 対応 Android バージョン、必要な機器、UUID の一覧、ビルド手順、既知の問題を書く。

## 7. 振り返り

演習の最後に次の点を書き出し、次の開発に生かします。

- 予定どおりに進んだステップと、時間がかかったステップ。その理由。
- 見つかった不具合と、どのテストで見つかったか（見つけられなかったものはないか）。
- 設計で良かった点・直したい点（例: BLE の処理を分けておいて助かった、キューを最初から作るべきだった）。

## セルフチェック

1. Activity に BLE の処理を直接書かず、別クラスに分ける理由は何か。
2. JUnit で単体テストしやすいのは、どのような処理か。この演習の例を挙げよ。
3. 実機テストで確認すべき異常系を 3 つ挙げよ。
4. アプリと BLE 機器のどちらに問題があるかを切り分けるには、何を使うとよいか。
5. リリース用の署名鍵を Git に入れてはいけない理由は何か。

<details>
<summary>答え</summary>

1. 画面は表示と操作だけに集中でき、通信処理を他の画面から再利用・単体でテストしやすくなる。画面の作り直し（回転）の影響も受けにくい（単一責任）。  
2. Android に依存しない、入力から出力が決まる処理。例: `TemperatureParser`（バイト列から温度への変換）。  
3. 権限の拒否、Bluetooth がオフ、機器の電源断などによる途中切断（ほかに電波が届かない、機器が見つからない）。  
4. nRF Connect for Mobile（同じ操作が nRF Connect でできるなら、アプリ側の問題）。  
5. 鍵が漏れると第三者が正規のアプリを装った更新版を作れてしまうため。鍵は安全な場所に保管する。
</details>
